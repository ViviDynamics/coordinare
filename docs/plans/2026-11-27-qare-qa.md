# Let the QA persona run on QAre, opt-in

Issue #404

## Scope
In:
- The #402 stage contract applied to QA: the request also carries the base, the work item
  and its acceptance criteria with ids stable across heads; the outcome also carries every
  criterion's outcome and evidence. The QA evidence floor (a pass needs every criterion
  proven) and post-after-head-check publishing live in the adapter, so any QA provider is
  held to them. The reviewer path is unchanged.
- A QAre provider (`services/qare.py`) that runs the pinned QAre CLI as a detached local job
  per request id (`services/qare_runner.py`): checkout of head and base, `qare plan
  --criteria`, `qare run --plan` with posting off, `result.json` read with `schemaVersion`
  checked first.
- Coordinare posts the evidence (`services/qare_publish.py`): files on `qa-assets`, one
  comment on the pull request and the issue, each step idempotent.
- Config (`kind: qare`, `version` pin, `command`, `profile`, `work_dir`,
  `env_passthrough` by name), doctor and startup preflight checks, docs.

Out:
- Changes to QAre. Its SPEC's "A job handed in" example shows criteria without checks,
  which `qare run --job` does not plan; the provider plans first. Filed as ViviDynamics/qare#450.
- A dashboard view of QAre runs beyond the existing provider note on the config page.
- Several-profile (monorepo) jobs: one profile directory per repository for now.

## Assumptions
- QAre is a CLI, not a service, so "unreachable" is QAre that cannot start, and restart
  resumption is the job directory plus a runner process in a session of its own.
- `qare run --plan` builds the same job `qare run --job` takes (`jobFromPlan`, post `none`).
- `blocked`, `refused` and `waived` hold the card for a person. `waived` is a recorded
  human waiver, and QAre says a waiver is never a pass.
- No profile on either side holds the card with how to add one; no fallback to the
  built-in QA, which would hide a repository that is not set up.
- Exit 4, a missing result, a crash, a failed checkout or plan are retryable (nothing was
  posted). A result outside the contract (unknown `schemaVersion` or verdict, an exit code
  that contradicts the verdict) holds the card: retrying the same pinned release repeats it.
