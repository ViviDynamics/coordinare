# Research: Documenter Workflow for a Living Wiki That Humans and Agents Can Read

The documentation model (R-a to R-f) was researched on 2026-09-07 and agreed with the operator before the spec. The reuse seams (R-g to R-j) were resolved by reading the code on main `fae8a54`.

## R-a. One kind of documentation per page (Diátaxis)

**Decision**: every wiki page carries `kind: explanation | how-to | reference | decision` in frontmatter and its body must hold that kind's required headings; the gate refuses a page that mixes kinds by requiring the headings of exactly one.

**Source**: Diátaxis names four needs (tutorials, how-to guides, reference, explanation) and states that crossing or blurring the boundaries between them is the source of most documentation problems. Reference must not interpret or guide action; explanation serves understanding, not immediate tasks. [diataxis.fr](https://diataxis.fr/), [start here](https://diataxis.fr/start-here/). Tutorials are out of scope for a code wiki; decisions take the ADR shape (R-e).

## R-b. The index in the llms.txt shape

**Decision**: `docs/wiki/README.md` is generated by code: one H1 (project name), a blockquote summary under 300 characters, H2 sections (`Start here`, `Architecture`, `How to`, `Reference`, `Decisions`, `Optional`) whose bodies are `- [Title](page.md): one line` entries, every page linked exactly once.

**Source**: llmstxt.org: the H1 is the only required section, the blockquote holds the key information for understanding the rest, H2 sections group file lists, entries are `[name](url): notes`, the whole stays small enough to fit in context with detail behind links; the `Optional` section marks material an agent may skip. [llmstxt.org](https://llmstxt.org/). 2026 practice favours files under 5 KB that lead with the blockquote. [LLM Pulse guide](https://llmpulse.ai/blog/llms-txt-guide/).

## R-c. Progressive disclosure over pre-loaded prose

**Decision**: pages are short and cite paths; the README is an index, not an overview essay; pointer sections in `AGENTS.md` and `CLAUDE.md` are a template under 40 lines that links into the wiki.

**Source**: Anthropic's context engineering guidance: the smallest set of high-signal tokens, lightweight identifiers such as file paths for just-in-time loading, and structure (headings, hierarchy, naming) as the navigation aid; avoid pre-loading exhaustive information. [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Claude Code guidance on `CLAUDE.md`: include commands and quirks agents cannot guess, exclude anything derivable from code, API documentation ("link to docs instead"), changelogs and file-by-file descriptions; bloated files get ignored. [Claude Code best practices](https://code.claude.com/docs/en/best-practices). The empirical study of 2,303 context files: median 335 to 535 words, one H1 with 6 or 7 H2 sections; testing (76%), architecture (68%) and build commands (63%) dominate. [Agent READMEs](https://arxiv.org/abs/2511.12884). AGENTS.md conventions: overview, build and test commands, style, testing, security, PR rules; nearest file wins. [agents.md](https://agents.md/).

## R-d. Grounding, coverage and navigation are what generated wikis are judged on

**Decision**: every citation is re-extracted from the written content and checked against the tree; every wiki link must resolve; one concept has one home (the README links each page once; pages link rather than repeat); page counts are capped.

**Source**: CodeWiki structures wikis by module with dependency-aware ordering, keeps a global registry so components are cross-referenced instead of duplicated, links to source, and is scored on accuracy, coverage and navigability; generated documentation fails on stale claims and invented APIs. [CodeWiki](https://arxiv.org/abs/2510.24428). DeepWiki caps wikis at 30 pages by default, starts from high-level overview pages, and links every page to source. [DeepWiki docs](https://docs.devin.ai/work-with-devin/deepwiki).

## R-e. Decisions in the ADR shape

**Decision**: `docs/wiki/decisions/<slug>.md` with `kind: decision` and the headings `Context`, `Decision`, `Consequences`, `Status`; consequences must include costs (persona rule).

**Source**: Nygard's format (Title, Status, Context, Decision, Consequences) with negative consequences in the same section; MADR adds options when alternatives matter; pick the lightest format the team keeps current. [adr.github.io](https://adr.github.io/).

## R-f. Style rules both readers parse

**Decision**: exactly one H1; unique descriptive headings in sentence case with no links or inline code; fenced code blocks with a language; informative link text (never `here` or `link`); explicit repository paths for internal links; tables only for uniform reference data; plain repeated sentence shapes; explicit negative rules and one correct example over prose.

**Source**: Google's documentation style guide (document skeleton: title, short introduction, topic sections, see also; heading rules; fenced blocks; link text). [Google docguide](https://github.com/google/styleguide/blob/gh-pages/docguide/style.md), [headings](https://developers.google.com/style/headings). Stack Overflow on guidelines for agents and people: be simple, explicit and boring; show correct and incorrect examples; state negative rules. [Stack Overflow](https://stackoverflow.blog/2026/03/26/coding-guidelines-for-ai-agents-and-people-too/).

## R-g. The page set is chosen by code from the brief and the diff

**Decision**: `plan.build_plan(mode, brief, changed_files, inventory, layout, cap=8)`. The spec-165 documentation brief reaches the documenting stage as `Score.documentation_brief` with fields `summary`, `docs` (entries with `topic`, `location`, `say`) and `modules` (dispatch_performer.py:192, `_DOCUMENTATION_BRIEF_FIELDS`). The diff reaches it as `Score.pr_diff` because `tech_writer` is in `_DIFF_REVIEW_ROLES` (dispatch_performer.py:349); the reviewer's `parse_unified_diff` gives the changed files. A page is selected from the inventory when any of its citations equals a changed file or is a directory prefix of one.

## R-h. Evidence through the allow-list runner

**Decision**: gather reuses `architect.survey.run_survey_step`-style execution but with commands built by code, not proposed by the model: `sed -n '1,200p' <module>` for each brief module, `git show HEAD:<page>` for the current page, and the diff hunks from intake. Every command passes `allowlist.is_allowed` before it runs and is recorded. No model call in gather.

## R-i. One commit through the existing path

**Decision**: `performer.workspace.commit_files(stand, files, message, deletions=..., score=score)` (workspace.py:1333) writes, commits and pushes in one call and is what `_commit_doc_batch` uses today; the workflow builds the file list from surviving `write` results and the regenerated README and pointer sections, the deletions from accepted `retire` results, and calls it once. Before that, `write_free_check` (the reviewer's) proves the tree was clean at start, so an earlier stage's leftovers are never swept in. The init-mode PR open stays in main.py's `_commit_doc_batch` logic, which the workflow branch calls with the workflow's file list instead of re-implementing it.

## R-j. main.py mapping and the prose path

**Decision**: the documenting branch checks for `report["docs"]` with a known verdict (`docs_committed | env_blocked`) before the prose plan-then-write path; a prose model that emits a `docs` key without a verdict stays on the prose path (the spec-170 review lesson). `docs_committed` carries `files_modified` from the record so coordinare's noop rule (monitor_performer.py:4004) and the last-documented SHA keep working. Without the flag, `doc_phase`, `_advance_doc_writes` and `_commit_doc_batch` are untouched.
