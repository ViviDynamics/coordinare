## Overview

This is a recurring QA-and-optimization cycle (following 062, 065, 076), opened immediately after the **081 config-UI** feature (live config editing in the dashboard — tabbed `/config` view + reference dropdowns over the `/api/config/*` write service) landed on `main` (PR #99, squash `b7785ab`).

The cycle starts as an **open collector**: no seed bug is recorded yet. Each finding surfaced during live testing is appended below as its own prioritized user story with a concrete repro and an independent test, in the same shape as prior QA cycles. The branch collects **fixes only** — renames, new features, and larger refactors get their own spec (per project PR-scope discipline).

## Scope & Discipline

- **Fixes only.** This branch accumulates bug fixes and small optimizations discovered during live testing. Anything that is a new capability or a structural redesign is split into its own spec.
- **TDD.** Every fix lands with a failing test first (RED), then the fix (GREEN), per project convention.
- **One story per finding.** Each finding becomes a prioritized (P1/P2/P3) user story with: plain-language journey, *Why this priority*, *Independent Test*, a *Concrete Repro* where one exists, and *Acceptance Scenarios*.
- **No merge to `main`** without explicit direction and green CI.

### User Story 1 — persona_bench bypassed the 080 orchestration block (Priority: P1)

While preparing the dual-model (planner+executor) live benchmark, the persona-capability harness (`scripts/persona_bench.py`) was found to build its performer `/jobs` payload without ever emitting the `metadata.orchestration` block that spec-080 dual-model dispatch requires. As a result, any role configured with a non-`single` strategy would silently run as a plain single-model job under the benchmark — the in-container `DualModelProxy` was never engaged. The benchmark would therefore "validate" a planner+executor combo that never actually ran, producing false-positive results.

**Why this priority**: Correctness of the whole dual-model validation effort depends on it. A benchmark that silently degrades to single-model gives misleading confidence before we start coordinare for real.

**Independent Test**: `tests/unit/test_persona_bench.py::TestBuildJobPayload` — `build_job_payload(...)` with a non-None `orchestration` must place it at `payload["metadata"]["orchestration"]`; with `orchestration=None` the key must be absent. The test FAILS if the payload omits orchestration for dual-model roles.

**Acceptance Scenarios**:

1. **Given** a role bound to a `strategy: always` mode, **When** the harness builds its `/jobs` payload, **Then** `metadata.orchestration` carries the planner/executor legs (`thinking`/`tool`) exactly as live dispatch emits them.
2. **Given** a role bound to a `strategy: single` mode, **When** the harness builds its payload, **Then** no `orchestration` key is present.

### User Story 2 — persona_bench resolved the model via pre-080 `performers.<role>.model` (Priority: P1)

The harness (and `scripts/smoke_backends.py`) resolved the dispatch model by reading the legacy inline `performers.<role>.model` field, which is empty against an 080 catalog config (where the model lives in `modes → model_endpoints → endpoints`). Against the live config this yielded an empty model string, so the benchmark could not dispatch the intended planner/executor models at all.

**Why this priority**: Same root cause class as US1 — the harness was not 080-aware, so the live benchmark could not be trusted to exercise the configured models.

**Independent Test**: `tests/unit/test_persona_bench.py::TestResolveRoleDispatch` — `resolve_role_dispatch(config_path, "architect")` must return the executor-leg model (`spark/qwen3.6:35b`) and a populated `orchestration` block, mirroring `ProjectConfiguration.resolve_performer_dispatch_model` + `resolve_performer_orchestration`. A single-model role returns its model with `orchestration is None`. FAILS if resolution falls back to the empty pre-080 field.

**Acceptance Scenarios**:

1. **Given** an 080-catalog config, **When** `resolve_role_dispatch` is called for a dual-model role, **Then** it returns the executor model and the orchestration block.
2. **Given** a role with only a legacy inline `performers.<role>.model`, **When** `resolve_role_dispatch` is called, **Then** it falls back to that inline value (backward compatibility).

### User Story 3 — openclaw dual-model executor leg misrouted to the wrong endpoint (Priority: P1)

During the dual-model live benchmark, the `reviewer` role (backend `openclaw`, mode `plan120-exec-qwen36`, `strategy: always`) crashed the performer subprocess. Root cause: openclaw wrote its provider config with the **Ollama-direct** base URL (`http://192.168.3.30:11434/v1`, `provider=sparkollama`) while keeping the **LiteLLM-prefixed** model name `spark/qwen3.6:35b`. Ollama-direct only serves bare model names (no `spark/` prefix), so the request returned `404 model 'spark/qwen3.6:35b' not found` and the embedded run surfaced a `FailoverError`, exiting `rc=1` (`harness:subprocess_exit`). The executor leg's endpoint (`exec-qwen36 → spark-litellm`) was not honoured: openclaw resolved its own endpoint and paired it with the wrong model string, and it talked to Spark directly rather than through the in-container `DualModelProxy`.

**Why this priority**: A backend that silently rebinds the executor leg to the wrong endpoint defeats dual-model dispatch entirely and crashes the job. Any `always`/`conditional` role on openclaw is unusable until the endpoint/model pairing is consistent.

**Independent Test**: Given an 080 mode whose `tool` leg resolves to `{endpoint: litellm (base_url .../v1), model: "spark/qwen3.6:35b"}`, when the openclaw backend builds its provider config for a non-`single` strategy, then the written `base_url` and `model` must come from the **same** resolved upstream ref (litellm base_url ↔ `spark/qwen3.6:35b`), or the backend must point at the in-container `DualModelProxy`. FAILS if the base_url is the Ollama endpoint while the model retains the `spark/` prefix.

**Concrete Repro** (observed live 2026-06-07 13:31): job `211e4e6d8d254617ab8f9118e200be16`, branch `fix/reviewer-offbyone` on `conductor-bench`. Container log: `openclaw.provider_config_written base_url=http://192.168.3.30:11434/v1 provider=sparkollama` then `openclaw failed rc=1 ... 404 model 'spark/qwen3.6:35b' not found`. Captured at `specs/077-multi-backend-qa/persona_runs/082-dual-reviewer/cells/reviewer__openclaw-ephemeral.json`. Reproduces on **both** `opencode` and `openclaw` backends.

**Root-cause update (2026-06-07, confirmed)**: This is **not** a code defect in the openclaw backend itself — it is the openclaw/opencode *symptom* of the systemic stale-image failure documented in **US8**. Because every `config.dualbench.yaml` endpoint pins `image: coordinare-performer:full` built `2026-06-05 10:45` — ~7h **before** the spec-080 dual-model wiring landed (`7f69689`, `2026-06-05 17:13:02`) — `maybe_launch_proxy` never ran in any cell (`dual_model_proxy.launched` appears in **zero** round-2 cells). With no proxy, each backend independently picked one leg of the dual config: pi/codex resolved the executor endpoint (litellm base + `spark/qwen3.6:35b`) and reached a real model, while openclaw/opencode paired the **planner's** Ollama base_url (`192.168.3.30:11434`) with the **executor's** `spark/`-prefixed model → 404. The durable fix is the fail-fast guard in US8 (FR-008); a code fix to openclaw's pairing is only warranted if the 404 persists after re-running against a freshly-built image.

**Acceptance Scenarios**:

1. **Given** a dual-model role on openclaw whose `tool` leg is a LiteLLM endpoint, **When** the provider config is written, **Then** the model string and base_url belong to the same upstream ref (no Ollama base_url with a `spark/`-prefixed model).
2. **Given** a non-`single` strategy, **When** openclaw dispatches, **Then** it routes through the in-container proxy rather than resolving its own Spark endpoint.

### User Story 4 — JSON-repair retry drops the original task context (Priority: P2)

The `security` role (backend `pi`, mode `plan120-exec-qwen36`) produced a coherent prose verdict on its first attempt ("Security review complete… Both critical injection vulnerabilities have been fully remediated…") but not a JSON object. The harness re-prompted once to repair the output (`backend.invalid_output.retrying attempt=1`), but the repair prompt **lost the original task context** — the model's second reply was a generic fresh-session message ("I don't have any previous conversation about security vulnerabilities, SQL injection, or a `lookup_user` function… What would you like to work on?"), which also failed to parse, yielding `BACKEND_FORMAT_ERROR` after 2 attempts. The retry should re-issue the schema demand **with the prior turn(s) still in context** so the model reformats its existing answer rather than starting cold.

**Why this priority**: P2, not P1 — the underlying JSON-contract miss is a known `spark/qwen3.6:35b` model gap (see MEMORY.md), so even a perfect retry may still fail for this model. But the context-losing retry is a harness defect that turns a *recoverable* "reformat this as JSON" into an unrecoverable cold restart, and it masks the real signal (the model DID do the analysis). Fixing it improves every contract-bound role on every model.

**Independent Test**: Given a backend whose first turn returns non-JSON prose, when the JSON-repair retry fires, then the retry request must include the prior assistant output (or full conversation) so a follow-up like "return that as JSON matching the schema" is answerable. FAILS if the retry is a standalone prompt with no reference to the first turn (detectable when the model replies as if it has no prior context).

**Concrete Repro** (observed live 2026-06-07 13:32–13:34): job `e0aa25845d7a4d13964354ee9defdd6b`, branch `feat/security-sqli`. First output preview: "Security review complete. My independent analysis confirms…"; retry output: "I don't have any previous conversation…". Captured at `specs/077-multi-backend-qa/persona_runs/082-dual-pi/cells/security__pi-ephemeral.json`.

**Acceptance Scenarios**:

1. **Given** a non-JSON first turn, **When** the repair retry is built, **Then** it carries the prior turn in context.
2. **Given** the retry carries context, **When** the model reformats, **Then** a valid first-turn answer is preserved rather than replaced by a context-free reply.

### User Story 7 — implementer cell graded PASS but reported state=failed/status=error (Priority: P2)

The `implementer` role (backend `codex`, mode `plan120-exec-qwen36`) was graded **PASS** by the deterministic grader (tests_pass, "4 passed") yet the job's terminal `state=failed` / `status=error`. The grader and the job-state machine disagreed about the same run. Either the grader is reading a stale/partial artifact and passing a job that actually errored, or a successful implementation is being marked failed by a post-success step (e.g. CI/verify or PR handoff). This must be root-caused before trusting any implementer benchmark verdict.

**Why this priority**: P2 — a grader/state disagreement undermines confidence in every PASS the harness reports. If the grader can call a `failed`/`error` job PASS, false positives leak into the validation we are running specifically to gain confidence before going live.

**Independent Test**: Given a cell whose job terminal `state=failed`/`status=error`, when the harness categorises it, then it must NOT be reported PASS without an explicit reconciliation rule (and that rule must be documented). FAILS if grader truthiness alone overrides a terminal error state.

**Concrete Repro** (observed live 2026-06-07): `implementer`/`codex` cell in the 082 dual-model diagonal run — grader tests_pass / "4 passed", judge 4, but `state=failed`, `status=error`.

**Acceptance Scenarios**:

1. **Given** a job with terminal error state, **When** categorised, **Then** the category reflects the error (or an explicit, documented reconciliation) rather than a bare PASS.
2. **Given** a genuine post-success failure (CI/PR step), **When** the implementer finishes, **Then** the state machine and grader agree on the outcome.

### User Story 8 — dual-model benchmark silently ran pre-080 code on a stale image (Priority: P1)

The entire dual-model live benchmark ran against a **stale performer image** that predates the spec-080 dual-model wiring, so no cell ever launched a `DualModelProxy` and every "dual-model" result is invalid. Every endpoint in `config.dualbench.yaml` pins `image: coordinare-performer:full`; that image was built `2026-06-05 10:45`, ~7 hours **before** the 080 wiring commit `7f69689` landed at `2026-06-05 17:13:02`. The client side is correct — `resolve_role_dispatch`/`build_job_payload` inject the full `metadata.orchestration` block (US1/US2 fixes verified live) — but the *performer* code inside the container had no `maybe_launch_proxy` support, so the proxy never started. Confirmation: `dual_model_proxy.launched` appears in **zero** round-2 cells. Without the proxy, each backend silently degraded to single-model by binding one leg of the split config (the US3 404 and the misleading US4/US5/US7 verdicts are all downstream of this). This matches the MEMORY.md warning that a stale `:full` image ships old performer source even after a rebuild of other layers.

This story carries two distinct fixes: (a) a **process/harness** fix — rebuild `coordinare-performer:full` from current source *before* any dual-model benchmark and re-run, treating the prior dual-model results as invalid; and (b) a **durable product** fix — a fail-fast guard so that a non-`single` strategy which does not successfully launch a proxy errors loudly (the job fails with a clear orchestration error) instead of silently degrading to single-model with a mismatched base_url/model pairing.

**Why this priority**: P1 — this invalidates the whole dual-model validation effort, which is the reason this cycle exists ("validate the combo of planner and executor works… before we start coordinare for real"). Silent dual→single degradation is exactly the false-confidence failure the benchmark was meant to prevent.

**Independent Test**: `tests/unit/test_proxy_launch.py` (or equivalent) — given a non-`single` orchestration strategy on a supported backend, when the proxy fails to launch (or is absent), then `maybe_launch_proxy`/`handle_dispatch` must raise a clear orchestration error rather than returning `None` and proceeding single-model. FAILS if a non-`single` strategy proceeds with the provider base_url unset/mismatched and no proxy. Separately, a harness-level guard asserts the resolved performer image was built at/after the 080 wiring (or carries a capability marker) before a dual-model run starts.

**Concrete Repro** (confirmed 2026-06-07): image `coordinare-performer:full` digest built `2026-06-05 10:45` < 080 commit `7f69689 2026-06-05 17:13:02`. Across all `082r2-*` cells under `specs/077-multi-backend-qa/persona_runs/`, `grep dual_model_proxy.launched` over the captured `container_logs` returns **no** matches.

**Acceptance Scenarios**:

1. **Given** a non-`single` strategy on a supported backend, **When** the in-container proxy cannot be launched, **Then** the job fails with an explicit orchestration error (no silent single-model fallback).
2. **Given** a dual-model benchmark run, **When** the harness selects the performer image, **Then** it verifies the image carries 080 proxy support (build time ≥ wiring commit, or an explicit capability marker) before dispatching, and aborts with a clear message otherwise.
3. **Given** a freshly rebuilt `coordinare-performer:full`, **When** a `strategy: always` cell runs, **Then** `dual_model_proxy.launched` is present in the container log and the provider base_url points at the in-container proxy.

### User Story 9 — DualModelProxy serves only two wire paths; OpenAI-style and Responses-API backends get 404 (Priority: P1)

Now that US8 is fixed (the proxy actually launches on the rebuilt image), the dual-model path works **only for claude_code** (Anthropic wire). Every other backend gets a `404` *from the proxy itself*, because the in-container `DualModelProxy` registers exactly two front-door routes — `/v1/messages` (Anthropic) and `/v1/chat/completions` (OpenAI Chat Completions) — and nothing else. Two distinct mismatches surface:

1. **Path-prefix mismatch (opencode, openclaw).** These backends point at the proxy correctly but call `/chat/completions` (no `/v1` prefix). opencode: `provider_config_written base_url=http://127.0.0.1:37013`, then request to `http://127.0.0.1:37013/chat/completions` → `404: Not Found` (`server: aiohttp/3.14.0` — i.e. the proxy, not an upstream). openclaw: base_url correctly `http://127.0.0.1:33615` (the old US3 Ollama misroute is GONE), then `FailoverError: HTTP 404: 404: Not Found`.
2. **Wire-format gap (codex).** codex speaks the OpenAI **Responses API** and calls `http://127.0.0.1:37857/responses` → `404 Not Found` — a path the proxy does not implement at all.

Desired steady state: a non-`single` strategy works end-to-end for every backend the catalog allows to run dual-model, not just claude_code. The proxy must accept the wire paths its supported backends actually call (at minimum: tolerate the missing `/v1` prefix on Chat Completions; serve `/responses` for Responses-API backends, or the backend's provider config must be normalized to a path the proxy serves).

**Why this priority**: P1 — this is the genuine spec-080 product gap that US8's stale image was masking. With it open, "dual-model" is claude_code-only; codex/opencode/openclaw cannot be planner+executor at all. That directly blocks the cycle's goal of validating planner/executor combos across personas before live coordinare.

**Independent Test**: `tests/unit/test_dual_model_proxy_routes.py` (or equivalent) — POST to the proxy on each path a supported backend actually uses (`/chat/completions` without `/v1`, and `/responses`) and assert it is routed/normalized rather than returning 404. FAILS if the proxy only matches the exact strings `/v1/messages` and `/v1/chat/completions`.

**Concrete Repro** (confirmed 2026-06-07, rebuilt image): all `082r2-*` cells show `dual_model_proxy.launched` x1. claude_code → `dual_model_proxy.request path=/v1/messages status=200` (works). opencode → proxy `404` at `…/chat/completions`. openclaw → proxy `404` (FailoverError). codex → proxy `404` at `…/responses`. pi → **no `dual_model_proxy.request` logged at all**, `invalid_output.retrying failure_reason='was empty'` within ~3s of `pi started`, then BACKEND_FORMAT_ERROR — i.e. the same transport wall, swallowed by pi's backend into an empty response rather than a surfaced 404 (so pi is a US9 variant, NOT a genuine US4 context-loss case). Evidence in `specs/077-multi-backend-qa/persona_runs/082r2-{reviewer,security}-{opencode,openclaw,codex,pi}/cells/*.json`. Proxy route table: `agent/performer/src/performer/proxy/dual_model_proxy.py:47` `_PATH_WIRE = {"/v1/messages": "anthropic", "/v1/chat/completions": "openai"}`; `proxy/shim.py:45` `_FRONT_DOOR_PATHS = ("/v1/messages", "/v1/chat/completions")`.

**Acceptance Scenarios**:

1. **Given** a dual-model opencode/openclaw cell, **When** the backend calls the proxy at `/chat/completions` (no `/v1`), **Then** the proxy routes it as OpenAI wire and relays upstream (status 200), not 404.
2. **Given** a dual-model codex cell, **When** codex calls the proxy at `/responses`, **Then** the proxy either serves the Responses API or the codex provider config is normalized to a served path — no 404.
3. **Given** any backend the catalog permits to run dual-model, **When** a `strategy: always` cell runs end-to-end, **Then** the run reaches the model (no proxy-level 404) and the cell's failure, if any, is model/quality — not transport.

### User Story 10 — junie dual-model handed the bare proxy root and its standalone build fails (Priority: P1)

A new combo probe (`082r10`, assessor role on `junie-ephemeral`, dual `plan120-exec-qwen36`, `strategy: always`) **ERRORed** before any inference. The `DualModelProxy` launched correctly on junie's own one-shot harness (`dual_model_proxy.launched backend=junie env_var=JUNIE_PROVIDER_BASE_URL strategy=always`), but junie died ~4 s later at `Failed to build 'issue.md.junie_standalone'` — `junie started` (18:28:27) → `junie stopped` (18:28:31), with **no** `dual_model_proxy.request` ever logged. The proxy was wired but junie never reached it.

Root cause: junie is the one backend that POSTs **verbatim** to `JUNIE_PROVIDER_BASE_URL` (`agent/performer/src/performer/backends/junie.py` requires the FULL endpoint URL — e.g. `https://host/v1/chat/completions` — and appends no path of its own). But `maybe_launch_proxy` (`proxy/launch.py:268`, `target[env_var] = base`) uniformly handed junie the **bare** proxy root (`http://127.0.0.1:PORT`), and `DualModelProxy.start()` returns a bare root while the proxy serves only pathed front doors (`_PATH_WIRE`: `/v1/chat/completions`, `/chat/completions`, …) — never bare `/`. So junie's standalone-build POST to `/` missed every served route and the build crashed before inference. Other backends (codex/opencode/openclaw/pi/claude_code) build their own path off the base, so the bare root is fine for them; junie is uniquely broken by it.

Attribution was locked with a single-mode control (`082r10c`, identical cell, `mode: single-gptoss120-ollama`): single mode reached `status=assessment_complete` (junie built its standalone issue, ran ~60 s, committed `assessment.md`, succeeded — only FAIL_MODEL on the known JSON-gate model gap, **no** standalone-build error). Therefore the dual ERROR is a **dual-mode regression**, not pre-existing junie flakiness.

**Why this priority**: P1 — same class as US9 (a transport-layer proxy gap that blocks a backend from running dual-model at all). With it open, junie cannot be planner+executor: any non-`single` strategy on junie crashes at the standalone build before reaching the model.

**Independent Test**: `agent/performer/tests/unit/proxy/test_launch.py::test_junie_provider_base_url_carries_full_wire_path` — for `backend=junie`, `maybe_launch_proxy` must set `JUNIE_PROVIDER_BASE_URL` to a full served endpoint ending `/v1/chat/completions`, not the bare proxy root. Plus `test_verbatim_post_backends_use_a_served_proxy_path` — every verbatim-POST suffix must be a path the proxy actually serves (`_PATH_WIRE`). FAILS if junie is handed the bare root.

**Concrete Repro** (observed live 2026-06-07): dual `082r10-assessor-junie` → `category=ERROR`, `status=error`, `reason="Junie failed with the message: Failed to build 'issue.md.junie_standalone'"`; container log `dual_model_proxy.launched backend=junie … strategy=always`, `junie started … pid=81` then `junie stopped` ~4 s later, no `dual_model_proxy.request`. Control `082r10c-assessor-junie-single` → `state=succeeded`, `status=assessment_complete`, no standalone-build error. Both captured under `specs/077-multi-backend-qa/persona_runs/`.

**Acceptance Scenarios**:

1. **Given** a dual-model junie cell, **When** `maybe_launch_proxy` redirects junie at the proxy, **Then** `JUNIE_PROVIDER_BASE_URL` carries the full served wire path (`…/v1/chat/completions`), not the bare root.
2. **Given** junie's standalone build POSTs verbatim to that URL, **When** the build runs, **Then** it hits a served front-door path (no `Failed to build 'issue.md.junie_standalone'` before inference).

### User Story 12 — reasoning-vs-instruct executor sweep is unrankable on security/pi: the card never reliably delivers the task to the executor (Priority: P2 / model+bench-card finding)

The user asked to "run the bench again using a few different reasoning-only models and the instruct model to see how they do." `082r13` ran a controlled 4-leg sweep on the hardest contract-bound persona (security / pi-ephemeral), holding everything constant except the **executor** leg — planner fixed at `gpt-oss:120b` (Ollama-direct), `strategy=always`, `expose_plan_as=thinking`, same committed security card — and varying only the tool model across `{spark/qwen3.6:35b, spark/qwq:32b, spark/deepseek-r1:32b, spark/qwen2.5:14b-instruct}` (each leg from a temp config copy so the tracked `security.mode` never churned; harness `tmp/082r13_sweep.sh`).

**All four legs FAILED — but for three distinct reasons, none of which is a clean reasoning-vs-instruct quality ranking:**

- **`082r13a` (qwen3.6:35b, reasoning):** transport GREEN — `dual_model_proxy.launched backend=pi strategy=always`, then 2× `dual_model_proxy.request path=/chat/completions status=200` (30.1 s + 32.0 s — proof both `think()` and `act()` ran end-to-end). The executor nonetheless returned a generic greeting (`"Hello!
